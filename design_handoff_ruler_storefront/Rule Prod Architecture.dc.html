Build & deploy architecture

A five-service demo storefront on Kubernetes, delivered by Argo CD from Git.

1. One repo, not five

Use a single application repo, github.com/mezmo-demos/ruler-shop. Five separate repos buy you independent release cadence — which a demo does not need — and cost you a five-way pull request every time a shared contract changes. The one split worth making is app code versus cluster config, because Argo writes to the config repo and you don't want image-tag commits retriggering CI.

mezmo-demos/ruler-shop/
├── services/
│   ├── frontend/     Dockerfile, src/     Next.js — UI + BFF
│   ├── catalog/      Dockerfile, src/     products, prices, price breaks
│   ├── cart/         Dockerfile, src/     active + saved carts
│   ├── checkout/     Dockerfile, src/     order placement, promo codes
│   └── orders/       Dockerfile, src/     order history
├── libs/shared/      logging, tracing, error taxonomy
├── loadgen/          synthetic shopper traffic
└── .github/workflows/build.yml

mezmo-demos/ruler-shop-gitops/
└── services/
    ├── cart/{deployment,service}.yaml
    ├── catalog/{deployment,service}.yaml
    ├── checkout/{deployment,service}.yaml
    ├── frontend/{deployment,service}.yaml
    └── orders/{deployment,service}.yaml

2. Images in GHCR, not "in GitHub"

GitHub's container registry is GHCR. Push to ghcr.io/mezmo-demos/ruler-shop/<service>:<sha>. It's free for public images, scoped to the org, and authenticates from Actions with the built-in GITHUB_TOKEN — no external registry credentials to rotate.

Tag by commit SHA, never :latest. A mutable tag means the cluster and Git disagree about what's running, which is the one thing GitOps exists to prevent — and it makes "when did this regression ship?" unanswerable, which matters for an observability demo.

.GITHUB/WORKFLOWS/BUILD.YML — SHAPE
strategy:
  matrix:
    service: [frontend, catalog, cart, checkout, orders]
steps:
  - detect changed paths (skip unchanged services)
  - docker buildx build ./services/${{ matrix.service }}
  - push ghcr.io/mezmo-demos/ruler-shop/${{ matrix.service }}:${{ github.sha }}
  - yq -i '.spec.template.spec.containers[0].image = "…:${{ github.sha }}"' \
      ../gitops/services/${{ matrix.service }}/deployment.yaml
  - commit & push to ruler-shop-gitops

3. Argo picks it up

Your directory layout works as-is with a single Application using recursive directory sync — Argo applies every YAML under services/. If you want per-service health, sync status, and rollback in the Argo UI (worth it for a demo you'll be showing on screen), use an ApplicationSet with a git directory generator instead: one child Application per service directory, generated automatically as you add services.

Either way, keep the CI commit as the only thing that changes an image tag. That commit is the deploy record, and it's what you point at when the demo shows a latency spike starting at 14:02.

4. Service responsibilities

SERVICE OWNS STATE
frontendAll six screens; server-renders pages and fans out to the other four. The only service exposed via Ingress.session cookie
catalogProducts, categories, facets, search, base price and the quantity price-break ladder. Read-heavy — the natural place to demo cache hit ratio.Postgres + Redis
cartActive cart per session, save-for-later lines, and named saved carts. Applies the break tier by calling catalog for the ladder.Redis + Postgres
checkoutValidates the cart, redeems promo codes, computes tax and shipping, writes the order, clears the cart. No card data is ever accepted — the "payment method" is an invoice stub.stateless
ordersOrder records, status transitions, history for the account page, and "buy again".Postgres
Checkout is the interesting service
It's the only one that touches three others in a single request, so it's where a demo actually gets to show a distributed trace worth looking at: frontend → checkout → cart → catalog → orders. Give it a deliberate failure surface — promo code expired, inventory drift between cart and catalog, orders write timeout — and every one of those becomes a legible incident with a real root cause.

5. Two things to settle early

Identity. Guest checkout plus optional accounts means every service needs to key off something that survives a guest becoming a user. Issue an anonymous session id at first request; on account creation, re-key the cart and back-fill the order. Do this in cart and orders from day one — retrofitting it is miserable.

Where price is computed. One service owns pricing arithmetic, and it should be catalog for unit price and breaks, checkout for order-level promos and tax. If cart also does the maths you get three implementations of the same rounding rule and a $0.01 discrepancy nobody can find.

6. Product photography

Every image slot in the designs is a labelled placeholder. Rulers are unusually well served by free stock — search "ruler", "tape measure", "carpenter square", "slide rule", "drafting tools" on:

  • Unsplash and Pexels — best for the wide hero flat-lays; strong on workbench and drafting-desk scenes.
  • Rijksmuseum and Smithsonian Open Access — public-domain scans of antique boxwood rules and slide rules, ideal for the vintage archive and unbeatable for the editorial direction.
  • Pixabay — the deepest well of plain white-background product cutouts for grid cards.

For a demo, consistency beats variety: shoot or pick everything on the same neutral background and one shadow direction, and the catalogue grid will read as a real store even with twelve products.
